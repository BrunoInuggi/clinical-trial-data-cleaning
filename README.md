
# Clinical Trial Adverse Events — Data Cleaning

This project is part of my data science portfolio. The goal was to practice and document a full data cleaning pipeline using SQL on Snowflake, applied to a simulated adverse events dataset.

The dataset was generated by a generative AI tool and intentionally seeded with data quality issues — orphan records, impossible dates, out-of-range doses, and more. Working through those problems is the point.

## Dataset

Three tables, simulated with realistic structure for an adverse events reporting context:

| Table | Rows | Description |
|---|---|---|
| `ADVERSE_EVENTS` | 10,000 | Adverse event reports — one row per event |
| `PATIENTS` | 3,000 | Patient demographics — age, sex, weight, diagnosis |
| `DRUGS` | 100 | Drug reference data — therapeutic class, approved dose range |

The dataset was generated by a generative AI tool and intentionally contains data quality issues across all three tables.

## Cleaning pipeline

The full pipeline runs in four sections. Raw data is never modified — each step produces a new view in Snowflake. That way the exclusion logic stays visible, auditable, and reversible.

### ADVERSE_EVENTS

| Step | View | Rows | Removed | Reason |
|---|---|---|---|---|
| Raw | `ADVERSE_EVENTS` | 10,000 | — | — |
| S1 | `ADVERSE_EVENTS_RI_CLEAN` | 9,043 | 957 | Orphan drug/patient IDs |
| S2 | `ADVERSE_EVENTS_LOGIC_CLEAN` | 4,119 | 4,924 | Event date before drug start date |
| S3 | `ADVERSE_EVENTS_CLEAN` | 3,748 | 371 | Invalid doses (negative, out of range) |
| S4 | `ADVERSE_EVENTS_FINAL` | 3,748 | — | Nulls flagged, `days_to_event` added |

**Final retention: 3,748 out of 10,000 events (37.5%)**

### PATIENTS

| Step | View | Rows | Removed | Reason |
|---|---|---|---|---|
| Raw | `PATIENTS` | 3,000 | — | — |
| S2 | `PATIENTS_CLEAN` | 2,707 | 293 | Age > 110 years |
| S4 | `PATIENTS_FINAL` | 2,707 | — | BMI calculated, quality flags added |

## Key decisions

These are the cases where the cleaning logic required more than just "this value is wrong."

**Event date before drug start date (54.5% of records)**
An adverse event can't occur before drug exposure begins — that's just not how pharmacology works. I considered trying to correct the dates, but without knowing which one is wrong, there's no defensible fix. Exclusion was the only clean option.

**Age > 110 years (9.8% of patients)**
The longest documented human lifespan is 122 years. I used 110 as a conservative threshold — anything above that almost certainly reflects a data entry error rather than a real patient. The cutoff is clinical, not arbitrary.

**Pediatric patients with weight > 100kg (7 cases)**
A child under 18 weighing over 100kg is unusual, but severe pediatric obesity exists and these cases can be clinically valid. Automatically excluding them could introduce bias in any subgroup analysis involving pediatric patients. I flagged them with a `data_quality_flag` column and left the exclusion decision to whoever uses the data downstream.

**Dose validation per drug, not by generic threshold**
Rather than applying a single cutoff across all drugs, I validated each dose against the approved range for that specific drug using the `DRUGS` reference table. A dose of 200mg might be fine for one drug and a dangerous overdose for another — a generic threshold would miss that entirely.

**Null doses retained (4.9% of events)**
A missing dose value doesn't mean the adverse event didn't happen. Patient-reported events often lack precise dosage documentation. Excluding null doses would skew the dataset toward hospital-reported cases and underrepresent self-reported events — which is a form of bias worth avoiding.

**Country field — not treated as an error**
`ADVERSE_EVENTS.country` and `PATIENTS.country` represent different things: where the event occurred vs. where the patient is from. A German patient having an adverse event while in the US is a real scenario. These were kept as separate fields rather than treated as a mismatch.
